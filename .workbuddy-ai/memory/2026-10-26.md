## 修复 /analytics 深色模式下文字发黑

**现象**：深色主题下统计页大量文字（卡片里的数字、说明、次要信息）仍是黑色，深色背景上几乎看不清。

**根因**：页面移植自 Aemeath 主题，全篇文字颜色写成
`color-mix(in oklab, var(--text-color) 92%, transparent)`，
但本项目根本没有 `--text-color` 这个变量。变量未定义 → `color-mix()` 整体无效 → `color` 属性失效 → 退化为继承，落在深色卡片里就是黑字。

**同类缺失变量**（一并补齐）：`--font-active-sans`、`--glass-control-border`。

**修复**（`src/pages/analytics.astro`）：
- 在 `.analytics-page` 作用域内显式定义 `--text-color: oklch(0.25 0.02 var(--hue))`，并在 `:root.dark .analytics-page` 覆盖为 `oklch(0.93 0.01 var(--hue))`，让文字随主题反转。
- 补 `--font-active-sans: inherit`、`--glass-control-border`（基于 `--line-divider`）。
- 把 `var(--deep-text)`（深色下不反转）改为 `var(--text-color)`。
- `AnalyticsSnapshot.astro` 同样补了 `--text-color` 兜底与深色覆盖。

**验证**：用无头浏览器读取 computed color，深色得到 `oklab(0.93 … / 0.92)`（浅色文字），亮色得到 `oklab(0.25 … / 0.92)`（深墨文字）。

**备注**：无头截图在本机不稳定，改用「注入探针脚本 + `--dump-dom` 读 `document.title`」的方式验证计算样式，比截图快且不会崩。

## Umami Cloud 导出包分析与迁移脚本

用户提供 Cloud 导出 zip（`website_event.csv` / `event_data.csv` / `session_data.csv`）。

**数据概况**：1585 条事件（pageview 1477 / event 105 / type5 3）、227 个 session、360 个 visit，时间跨度 2026-09-24 ~ 10-25，时间为 UTC。

**关键坑**：Cloud 导出的 `session_data.csv` 只有表头（是会话属性表，不是会话表本身），**导出包里没有独立的 `session` 表数据**；但 `website_event.csv` 是扁平化的 41 列，把 browser/os/device/screen/language/country/region/city/distinct_id 都塞在事件行里。所以必须按 `session_id` 聚合去重，自己拼出 `session` 表，否则自建库外键会失败。

**表结构（Umami v3，来自 prisma/schema.prisma）**：
- `session`: session_id, website_id, browser, os, device, screen, language, country, region, city, distinct_id, created_at
- `website_event`: 31 列（event_id, website_id, session_id, visit_id, created_at, url_path, url_query, utm_×5, referrer_×3, page_title, gclid/fbclid/msclkid/ttclid/li_fat_id/twclid, event_type, event_name, tag, hostname, lcp/inp/cls/fcp/ttfb）
- `event_data`: event_data_id, website_id, website_event_id, data_key, string_value, number_value, date_value, data_type, created_at（主键需自己生成 UUID）
- `session_data`: 有 `@@unique([sessionId, dataKey])`

**产出**：转换脚本 `convert.py`（标准库，按 session_id 聚合 + 换 website_id + 时间转 ISO8601 UTC + 生成 event_data_id），材料已整理到 `C:/Users/27563/Downloads/umami-migrate/`（含 README 导入命令）。

## 修复线上「推送节奏全是 0」

**现象**：部署后 `/analytics` 的推送热力图几乎空白。

**根因**：`src/pages/api/github-pushes.json.ts` 在构建期执行 `git log`，但 **Vercel 是浅克隆**，构建时只有 1 条提交。`vercel.json` 里加的 `git fetch --unshallow` 并没有生效（线上接口返回 commits 只有 1 条，source 仍是旧值），所以热力图等于只有一个格子。

**修复**：接口改为双通道 ——
- 先读本地 `git log HEAD --since="53 weeks ago"`，条数 >= 10 视为完整克隆，直接用（本地开发/CI 走这条）
- 否则回退 `GET https://api.github.com/repos/{repo}/commits?sha=master&since=...&per_page=100&page=N`，翻页直到不足 100 条
- 支持 `GITHUB_TOKEN` 环境变量（未认证限流 60 次/小时，一次构建约 16 次请求；配了 token 可提到 5000）
- 响应里 `source` 字段标明数据来自 `local-git` 还是 `github-api`，便于线上排查

**验证**：线上 `?t=时间戳` 绕缓存后返回 `source: github-api`、`commits: 1509`（2025-10-20 ~ 2026-10-26）。注意该接口 `Cache-Control: max-age=300`，部署后要等 5 分钟或带随机参数才看到新数据。
